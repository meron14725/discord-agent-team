## 3. 実装する構造

### 3.1 状態と永続データ

`src/agent_team/db.py` にv2用のテーブルを追加し、`src/agent_team/migrations.py` でschema version 2の明示的かつ再実行可能なmigrationを実装する。既存テーブルの意味を変えず、既存行は `workflow_version=1` として扱う。

追加・変更するデータは次のとおり。

| データ | 主な項目と制約 |
| --- | --- |
| Task拡張 | `workflow_version`、要件参照ID、現在の計画参照ID。既存行の既定値は1、新規v2は2 |
| RequirementsReference | task、GitHub repo/issue番号/URL、body hash、GitHub updated_at、状態。本文そのものは保存しない |
| PlanVersion | task、要件Issue参照、Issue内通算版、path、content hash、base SHA、review状態。`requirements reference+version`を一意化 |
| ApprovalGrant | task、工程、対象hash/SHA、confirmation ID、actor、期限、消費時刻。confirmation IDを一意化 |
| Consultation | task、安定したtopic ID、ordinal、質問と結論の安全化済み要約、Issue comment URL。`task+topic+ordinal`を一意化 |
| Delegation | task/topic、依頼元/先role、目的、期待成果、状態、内容hash、親依頼、Discord message IDs |
| ProjectWorkspace | GitHub repository、Discord channel ID。repositoryを一意化 |
| TopicThread | task、topic ID、thread ID、状態、resolved_at、archive_after、Issue comment URL |
| RepositoryLease | repository、job、owner、fence、lease期限。repositoryを一意化し、同一repositoryのwrite jobを直列化 |
| TaskProjection | task、project workspace、Discord status message ID、最終投影hash。taskを一意化 |
| ExecutionBudget | task、総model予約数、相談総数、計画修正数、実装修正数。taskを一意化し行ロックで更新 |

v2の主状態は次の順にする。

```text
DraftingRequirements
  -> AwaitingRequirementsConfirmation
  -> PlanningImplementation
  -> ReviewingImplementationPlan
  -> AwaitingPlanApproval
  -> Queued
  -> Implementing / Fixing
  -> Reviewing
  -> AwaitingChecks
  -> AwaitingMergeApproval
  -> ReadyToMerge
  -> Merging
  -> Merged
```

`Paused`、`Blocked`、`Cancelled` は全工程から遷移可能とし、`Cancelled` は終端状態にする。v2の再開要求は元taskを再利用せず、現在のIssueを参照する新しいtaskを作って前task IDを記録し、要件承認からやり直す。Issue本文が承認版から変わった場合は `DraftingRequirements`、計画が承認版から変わった場合は `PlanningImplementation`、PR head/baseが変わった場合は既存のレビュー・マージ承認失効処理へ戻す。状態遷移、承認消費、予算予約、相談回数、Delegation状態更新は同じDB transaction内で行う。

`Job.data` のfenceへ `workflow_version`、要件hash、計画version/hash、base SHAを含める。ジョブ完了時にもGitHubから要件Issueを再取得し、承認済み要件hashとの一致を確認する。古い結果は保存や外部送信を行わず破棄する。

オーナーのv2中止要求は `cancel` 専用transactionで処理する。工程別承認を失効し、queued job、未送信で副作用を起こすoutbox、未開始の外部operationをcancelし、running jobとrepository leaseのfenceを進めてworkerへcancelを通知してから `Cancelled` にする。Issue closeはtask IDを冪等keyにしたtrusted GitHub operationとして最大3回再試行し、失敗してもtaskを再開せずSREとオーナーへ通知する。すでに送信済みのIssue、branch、PR、artifact、audit、会話ログは削除しない。job完了・publish・cancelが競合しても、外部送信直前のtask lockとfence再検査により中止後のpublishを拒否する。

### 3.2 役割台帳と実行契約

新しい `src/agent_team/roles.py` に役割ID、表示名、責務、capability、tools、禁止操作、入力・出力schema、相談可能role、並列区分、fallback role、Discord bot key、worker endpointを持つ検証済みregistryを置く。`config.yaml` には初期8役を登録し、10役以上を追加できる形にする。

初期の互換対応は次のとおり。

| 既存接続 | v2 role ID |
| --- | --- |
| 統括Bot / coordinator | `coordinator` |
| 上流エンジニア / upstream | `cto` |
| 下流エンジニア / downstream | `backend_integrator` |
| 情シス・SRE / sre | `security_sre` |

`frontend_ux`、`qa`、`evaluation_manager`、`analyst` はregistry、prompt、endpoint、token環境変数、compose profileを実装し、Discord tokenがない間はdisabledにする。選定可能数は通常2〜4役とし、明示的な全員宛て会話だけ有効な全Botへ展開する。

`src/agent_team/contracts.py` の固定Literalをregistryで検証する文字列IDへ置き換え、用途別の型付きpayloadを追加する。

- RequirementsDraft / RequirementsQuestion / RequirementsApprovalRequest
- ImplementationHandoff
- ImplementationPlanResult / PlanReviewResult
- ConsultationRequest / ConsultationRecord
- DelegationRequest / DelegationResponse
- ExplanationRequest / ExplanationArtifact
- ApprovalCommand
- WorkspaceReadRequest / CommandRequest / PatchProposal

ワーカーは引き続き資格情報を持たず、各呼び出しを `--ephemeral` で開始する。trusted company policy、role policy、固定済みskill snapshot、Issue/計画の検証済み本文、相談要約だけを入力し、過去セッションは引き継がない。v2ではCodex CLIの一時sessionへrepositoryやhost toolを直接mountしない。モデルは必要なpath、test command、patchを `WorkspaceReadRequest`、`CommandRequest`、`PatchProposal` として返し、trusted control layerが実行する。file内容とstdout/stderrはsecret scanを通過した場合だけ、次の新しい一時sessionの入力へ含める。検出時は値を含まないblocked結果だけを渡す。これにより同一Codex session内のshellから未検査結果が直接モデルへ戻る経路を作らない。

Git上のrepository snapshotとモデル用contextを分け、制御層がcommit treeからrole/job別allowlistに合うregular text fileだけを選ぶ。選択した全fileをsecret scanしてからモデルへ渡し、binary、symlink、上限超過file、説明PNG、資格情報用pathはGit上に保持したまま内容を除外する。モデルへは選別manifestとして除外path、MIME、size、content hashだけを渡す。実装時はcontrol layerが提案patchを一時copyへ適用して検査・testし、検査済みtext差分だけをpublishするため、除外したbinaryを削除・置換しない。

control layerのcommand brokerはrepository設定にある固定argvだけを、資格情報・host filesystem・networkを持たないSandboxで実行する。shell文字列、任意実行ファイル、環境変数継承を拒否する。外部取得はtrusted adapterが行い、scan済み本文だけを次のmodel callへ渡す。read/command/patchの各roundも案件30回のmodel予算に含め、可能なpathとcommandを一つのrequestへbatchする。

### 3.3 GitHub Issue正本と要件定義

`src/agent_team/adapters/github.py` に、許可repository内のIssue作成、条件付き本文更新、コメント追加、再取得を追加する。publisherだけがこれらを行う。本文更新は `GET /repos/{owner}/{repo}/issues/{number}` で取得したETag、`updated_at`、body hashを記録し、`PATCH` に `If-Match: <etag>` を付ける。起動前の専用test Issueで、別更新後の古いETagによるPATCHが412となり、別更新の本文が保持されることを実環境preflightで確認する。GitHub側がこの条件を保証しない、ETagがない、または競合を検出した環境では自動PATCHを無効化し、変更案をIssue commentへ保存してownerによる本文反映を待つ。反映後の本文を再取得・検証してから続けるため、比較と更新の間の人手編集を自動処理が上書きしない。

`src/agent_team/requirements.py` を追加し、CTOの要件draftをIssue本文schemaへ整形し、必須節、未解決事項、AC IDの一意性とテスト可能性を検証する。`grilling` と `domain-modeling` の固定済みsnapshotは制御層がtrusted contextとして渡し、モデルに外部repositoryや個人skill directoryを読ませない。

オーナー判断が必要な論点だけ `TopicThread` を作り、推奨案と2〜3の選択肢を投稿する。自然文回答とボタン回答を同じ一回限りのconfirmation IDへ正規化する。24時間後の再通知は一度だけにし、未回答のまま先へ進めない。

要件完成時はGitHub Issue全体を再取得してhashを固定し、説明成果物生成へ進む。要件承認は承認者allowlist `requirements_approver_ids` で検査し、初期値は `312561681387487232` だけにする。会話を許可する `owner_ids` とは分ける。

### 3.4 内部相談と型付き引き継ぎ

`src/agent_team/consultations.py` と `src/agent_team/delegations.py` を追加する。内部相談は外部操作toolを持たないread-only workerで実行し、topic IDを制御層が発行する。agentはtopic IDを新規発行・変更できず、Discord topic thread、owner decision、親Delegationのいずれかに結び付いたimmutable IDを必ず継承する。表示名を変えても同じIDの回数を使う。新規topicは統括の型付き分類から一度だけ作り、origin event IDと正規化した目的hashの一意制約で名前変更や再送による重複を防ぐ。

同一topic 5回、task全体15回、モデル呼び出し全体30回を `ExecutionBudget` の行ロック内で予約してから実行する。計画修正数と実装修正数も別カラムで最大3回を予約し、そのmodel callを総数30回にも加算する。予約済み実行は失敗も回数に含め、再起動、並列呼び出し、新しい表示名で各上限を超えられないようにする。ChatGPT subscription modeでは既存の金額予約と日次30回制限を無効化し、案件30回とサービス側rate-limit/backoffだけを適用する。API key modeの金額上限は設定された場合だけ従来どおり適用する。

相談結果は、質問、判断材料、選択肢、推奨案、採用結果、未解決事項、参照資料だけを構造化してIssue commentへ保存する。モデルの非公開思考は要求も保存もしない。

要件承認後、制御層が最新Issue本文、承認記録、base SHAを再照合して `ImplementationHandoff` を作る。CTO Botからバックエンド／実装統合Botへの依頼を型付き `Delegation` として永続化し、同じtopic threadに相互メンション付きで依頼、受付、質問、回答、結果を表示する。Discord表示はoutboxの投影であり、全Botの `on_message` はbot/webhook投稿を無視し続ける。

既存の会社規則である専門役間の確認は最大2往復のまま維持する。内部相談の5回上限とは別カウンタにする。

### 3.5 実装計画、レビュー、説明、承認

`src/agent_team/planning.py` を追加し、バックエンド／実装統合workerが `docs/work-items/issue-<番号>/plans/v<版>.md` だけを変更するplan jobを実装する。版はtaskごとに1へ戻さず、同じ要件Issueに対する過去taskを含む通算連番をDB transactionで予約する。計画schemaは次を必須にする。

- 変更予定ファイルと責務
- 承認済みIssueから抽出した必須AC集合と自動・手動テストの対応
- テストコマンド
- secret、認可、冪等性、競合、権限の検討
- rollout、feature flag、migration、rollback
- 未確認事項

計画commit後、別job ID・別一時セッションのCTOが最新Issueと計画を取得してレビューする。必須AC集合は実行時に承認済みIssue本文から抽出し、重複IDと空集合を拒否する。critical/high/medium findingがなく、抽出した全ACのcoverage evidenceが過不足なくそろうまで承認しない。Issue #2ではその集合がAC-01〜AC-17になるが、汎用schemaへ17件を固定しない。修正往復は最大3回で、解決しない場合はオーナー判断topicを作る。

`src/agent_team/explanations.py` と資格情報を持たないrenderer processを追加する。固定済み `explain-visually` snapshotを要件完成後と計画レビュー完了後の2工程だけで呼び、個別質問や実装中には呼ばない。説明contractは、利用価値、対象範囲と対象外、通常フロー、権限・データ境界、復元困難な変更、主要失敗経路、受入条件、rollback、未解決事項を必須にする。rendererは固定templateとローカル資材だけを使い、入力HTMLをsanitizeし、CSPでscript・外部通信を禁止してHTML/PNGを生成する。制御層が生成前後にsecret scanを行い、source kind、source hash/version、HTML/PNG hashを `Artifact` に記録する。説明artifactのsource identityが現在の要件または計画と一致しなければ承認を出さない。最大2回の再試行後にだけ文章説明を作り、その文章hashに対するオーナーの別の明示承認がある場合だけ通常の説明gateを代替できる。

レビュー済み計画の説明をDiscordへ添付し、計画承認者allowlist、計画hash、base SHA、一回限りのconfirmation IDを照合する。承認後の計画変更は計画承認と未完了の実装・レビューを失効させる。

### 3.6 実装、PR、レビュー、マージ

既存 `src/agent_team/engine.py` の実装・レビュー・CI・マージ処理をv2 identityへ拡張する。実装開始時に、計画commit済みの案件branchからDraft PRを冪等に作成する。その後、新しい一時セッションの実装workerへ承認済みIssue本文、承認済み計画、base/head SHA、相談要約を渡す。

成果物検査は既存のpath、size、symlink、保護ファイル検査に加え、要件・計画の承認済みcopyと固定skill snapshotを変更禁止にする。実装結果をpublishする前に要件hashと計画hashをGitHubから再照合する。

実装後は別job・別セッションのCTOを必須reviewerとし、リスクに応じてQA、セキュリティ、フロントエンド、評価担当など最大4件のread-only reviewを並列実行する。結果を集約し、重大findingがあれば実装担当へ型付きで返す。修正は最大3回とする。全AC evidence、必須CI、branch protection、独立review、最新SHAへのオーナー承認がそろったときだけ既存mergerがSquash mergeし、確認済みmerge SHAを記録する。

Issue、計画、head SHAのどれかが変化した場合、該当工程以降の承認を同じtransactionで失効させ、実行中jobをfenceする。

実装とreview修正が終わったら、案件README、説明成果物、受入証跡をbranchへ反映して最終headを作る。そのheadでもう一度独立reviewと必須CIを完了してから `AwaitingMergeApproval` へ移り、repository write leaseを凍結する。以後、merge完了または承認失効まで自動処理はbranchへcommitしない。最新SHAへの承認はApprovalGrantとIssue comment、Discord statusに保存し、PR headを変えない。実際にbranch head/baseが変わった場合だけ承認を失効し、凍結を解除してreviewとCIからやり直す。merge SHAと完了状態はIssue comment、Discord status、DB監査へ記録し、承認後にREADMEを更新するための直接pushは行わない。

### 3.7 Discord作業空間とSRE

`src/agent_team/workspaces.py` とDiscord adapterを拡張する。`ProjectWorkspace` はrepository単位のchannel対応だけを持ち、task単位の `TaskProjection` が案件状態messageを1件ずつ持つ。同じrepositoryで複数taskが動いても別messageとして、状態、Issue、計画、PR、topic thread一覧を編集更新する。topic threadは目的ごとに作成し、解決から24時間後のarchive jobを登録する。再開時は同じthread記録を更新する。

制御層は要件参照、要件・計画承認、計画、説明artifact、consultation/decision comment、Discord threadのいずれかが確定するたび、`docs/work-items/issue-<番号>/README.md` の索引だけを決定論的に再生成して案件branchへ保存する。要件本文は複製しない。HTML/PNGはIssue内通算版に対応する規定pathへ保存し、Issue commentとDiscord thread URLを索引する。`AwaitingMergeApproval` へ入る直前に最終索引commitを作って以後のbranch投影を凍結し、マージ承認と完了通知はbranch外のDB・Issue・Discordだけを更新する。

READMEには「実行履歴」表を持ち、task ID、前task ID、状態、branch、最後のcommit SHA、使用した要件hash、計画版、説明hashを追記形式で残す。中止後の新taskは新しい通算計画版と、`agent/issue-<番号>-<短い名前>-r<実行番号>` の一意なbranchを使う。旧branchとcommitを削除せず、READMEとIssue commentから旧成果物へ到達できるようにする。更新はtask IDとcontent hashを冪等keyにし、同一repositoryの複数taskや同じIssueの再実行が現在行以外を置換しない。

outbox payloadを `status_projection`、`topic_message`、`delegation_message`、`approval_prompt`、`artifact_attachment`、`sre_audit` に型分けする。mention許可はpayloadで検証済みのowner IDまたはrole registryのBot IDだけに限定する。一般文字列からDiscord mentionを生成しない。

SREの型付き操作を、非公開GitHub repository作成、branch protection、required checks、Squash-only設定、直接push禁止、project channel作成まで拡張する。GitHub操作とDiscord操作は別planとして承認・実行し、それぞれbefore snapshot、digest、期限、事後snapshotを監査する。repositoryの公開化、role/permission変更、削除は個別承認がない限り実行しない。SRE特権queueはcapacity 1とし、通常workerへfallbackしない。

停止roleは、開始目標30秒を超えた時点からhealth確認を行い、最大5分の範囲で最大3回接続する。registryで同等capabilityかつ権限が強くないfallbackだけを選び、代替をtopic threadへ表示する。承認者とSRE特権操作はfallback対象外とする。通常poolの同時実行数はDBで予約し、同一repositoryのwrite jobは `RepositoryLease`、SRE特権jobは専用queueのcapacity 1で直列化する。ChatGPT認証時に全roleを一括直列化する現在の条件は除き、role別workerと分離したSandbox状態領域で最大4件を処理する。

Discord受信handlerは5秒以内に固定の受付messageを返し、モデル判定はその後のjobとして行う。queued_at、started_at、heartbeat_at、retry_count、escalated_atを永続化する。空きworkerがあるのに30秒以内に開始できなければ運用違反を記録しSREへ通知する。running jobは2分ごとに同じstatus messageを更新し、schedulerは仮想時計でも試験できる時刻providerを使って10分無更新を検出する。滞留jobはfenceして一度だけ再実行し、再び10分滞留したら `Blocked` にしてSREへDelegationを送りownerをmentionする。

GitHubのIssue保存・comment・版照合はtimeout、429、502、503、接続失敗だけを対象に、冪等keyを保ったまま1秒・5秒・30秒相当の設定可能なbackoffで最大3回試す。認可失敗、競合、schema不一致、hash不一致は再試行せず停止する。再起動後もoperationのattemptとnext_tryから継続し、打切り後はGitHub以外へ正本を作らずSREとownerへ通知する。

### 3.8 秘密情報の境界検査

`src/agent_team/redaction.py` に、既存token形式、PEM、Discord token、GitHub token、OpenAI key、一般的なcredential代入、設定可能な追加patternを検出する決定論的scannerを実装する。検出結果は種別、入力全体のsalted hash、位置を含むが、秘密値や周辺本文を保持しない。

次の境界すべてで同じscannerを呼ぶ。

1. Discord message受信直後、history構築前
2. repository snapshot、外部取得結果、model request構築前
3. model responseとworkspace artifact受領直後
4. GitHub Issue/comment/commit/PR body送信前
5. Discord本文・添付送信前
6. 説明renderer入力前と出力後
7. command brokerがstdout/stderr・file read結果を次のmodel sessionへ返す前、およびapplication logへ任意本文を渡す前

Discord受信で検出した場合は処理を開始せず、SRE Botの固定コードが対象messageを削除する。監査channelへguild/channel/message/author/time、検出種別、hash、削除成否だけを送り、オーナーへ該当credentialの失効・再発行を案内する。モデルに削除判断やBot tokenを渡さない。

repository scanの検証では、通常text file、dotfile、深いpath、test fixtureに失効済みtest credentialを置き、model session生成より前に拒否されることを確認する。command brokerでは、検査済み入力から実行時に検出対象のtest secretを組み立ててstdout/stderrとfileへ出すfixtureを使い、結果が次のmodel session、log、artifactへ含まれないことを確認する。モデルsessionにはrepository、command実行環境、scan前のtool resultをmountせず、環境変数一覧、host path、networkから秘密を取得できないsandbox testも行う。model応答やtest出力で検出した場合は後続model、GitHub、Discord、artifactへ渡さず、値を含まない失敗記録だけを残す。既存binaryと説明PNGを含むcommitからも次工程を開始でき、binary内容をmodelへ渡さず、publish後も同じblob hashで保持される往復testを追加する。

## 7. テストコマンドと手動確認

自動検証は最低限次を実行する。

```bash
python -m pytest
ruff check src tests
docker compose config
docker compose -f compose.yaml -f compose.sbx.yaml config
```

PostgreSQL migrationは、v1 fixtureからv2へ一度だけ適用、二重適用、旧task読み取り、v1/v2並行処理、失敗時のtransaction rollbackを専用integration testで確認する。

時刻要件は注入可能な仮想時計で、5秒受付、空き時30秒開始、2分heartbeat、10分滞留、一度だけの再実行、24時間再通知・archiveの境界値を試験する。実Discordではイベント受信、受付message、job開始、status editの時刻を監査IDで結び、p50/p95と違反件数を `docs/acceptance.md` に残す。

計画schemaはAC-01〜AC-17以外の番号と件数を持つfixtureでも検証し、承認済みIssueから抽出した集合だけがcoverage条件になることを確認する。

GitHub Issue更新はmockでIf-Match成功・412・header欠落を検証し、実環境preflightでは比較直後に別actorの編集を挿入して古いPATCHが失敗し、別actorの本文が保持されることを確認する。条件付き更新が保証されない場合は自動本文更新が無効になり、提案commentとowner反映待ち以外へ進まないことも受入条件にする。

中止と再実行は、running job完了との競合、未送信outbox、Issue close失敗を含めて試験する。同じIssueを2回中止・再実行し、計画版が通算で増え、一意なbranchとcommitから旧計画・説明・承認・相談記録へ到達でき、旧confirmation IDを新taskへ使えないことを確認する。

マージ前の順序は、最終索引commit後にreviewとCIを完了し、write freeze後に最新SHA承認を保存するfixtureで検証する。承認後のstatus・approval outbox処理ではcommitが増えずそのままmergeでき、実際にheadを変更した場合はwrite freezeを解除して承認・review・CIが失効することを確認する。

実Discord/GitHub確認は専用非公開test repositoryと「AIエージェント検証」categoryだけで行う。秘密情報試験には必ず失効済みのtest tokenを使う。公開化、既存channel削除、role変更、本番repository操作はこの受入試験に含めない。

## 8. セキュリティと運用上の確認点

- GitHub publisher/reviewer/merger、Discord Bot、Codex認証は既存どおり分離し、workerへmountしない。
- Issue本文、repositoryファイル、Discord履歴、外部skill文書はuntrusted dataとして扱い、会社規則を書き換えられない。
- vendor skillは指定commitとlicense hashをmanifestへ固定し、更新は別承認にする。
- plan/requirements/approval記録、company policy、role policy、CI、compose、config、migrationは実装agentの通常変更対象から除外する。
- rendererはnetworkなし、scriptなし、資格情報なしで実行し、生成物のpath、size、MIME、hashを検証する。
- status heartbeatとretryは冪等keyを使い、同じDiscord投稿、Issue comment、PR、mergeを重複させない。
- ログには本文を原則残さず、ID、hash、状態、error classを記録する。

## 9. 展開手順

1. DB backupを取得し、復元手順を確認する。
2. coordinatorとworkerの新規claimを停止し、running jobが完了またはfenceされたことを確認してから `agent-team migrate` を一度実行する。migration version 2を確認し、失敗時はtransaction rollbackして旧serviceを再開する。
3. v2 feature flagをoffのままv2対応service、worker、rendererを更新する。先にservice、次にrole別workerを起動し、旧workerはv2 jobをclaimできない状態で停止する。
4. health、旧v1 task、Discord通常会話、既存SRE変更をsmoke testする。
5. `discord-agent-team` repositoryと検証categoryだけを限定v2 allowlistへ追加する。
6. 現在の4 Botで第1〜3段階のend-to-end試験を実行する。失敗時は限定flagをoffにする。
7. SRE権限を必要最小限で追加し、heartbeat、滞留復旧、GitHub再試行、停止role、fallback、SRE直列化を現在の4 Botで有効化する。
8. AC-01〜AC-17と非機能要件の証跡がそろった場合だけ、新規正式依頼の既定をv2にする。既存taskはv1のまま完了させる。
9. 残り4 Botはtoken、role、channel visibility、worker healthを一役ずつ確認して有効化する。

## 10. ロールバック

- v2受付flagをoffにして、新しいv2 taskの作成を止める。
- 実行中v2 jobをfenceし、taskを`Paused`へ移す。Issue、branch、PR、artifact、auditは保持する。
- v1 taskと通常会話は旧経路を継続する。
- schema v2は加算的なので即時DROPしない。migration後は旧binaryへ戻さず、v2対応binaryの受付flagをoffにしてrollbackする。workerはworkflow versionに対応するjobだけをclaimするため、DBにv2行が残ってもv1 taskだけを安全に完走できることを試験する。
- Discord/GitHubに作成済みの安全な対象は自動削除しない。公開範囲や権限に問題があればSREの承認済み是正planで凍結・修正する。
- 再開時は元taskへ戻さず、前task IDと現在のIssueを参照する新しいtaskを作り、要件承認を取り直して計画と後続承認を再生成する。

## 11. 実装時の停止条件

次の場合は自動で先へ進めず、該当topic threadでオーナーへ報告する。

- 承認済みIssue hashとGitHub本文が一致しない
- migrationの後方互換性を保てない
- GitHubのbranch protectionまたは必須check発行者を検証できない
- SRE Botに必要権限がなく、安全な最小権限へ限定できない
- secret scannerが値の外部送信前遮断を保証できない
- rendererが外部通信または未検証scriptなしで再現できない
- 3回の計画修正または実装修正で重大findingを解消できない
- モデル実行、相談、再試行の上限へ到達した
- 第4段階の安全機構を含む全ACが検証categoryで完了していない

## 12. この計画で変更しないもの

- 進行中のv1案件は自動移行しない。
- GitHub Issue以外の要件正本を作らない。
- 全面的なDDD再編は行わず、Issue #1で段階的に進める。
- 内部相談役にDiscord Bot、外部操作権限、承認権限を与えない。
- Bot投稿を実行命令として読み直さない。
- 公開repository化、既存成果物の削除、管理者権限付与を自動化しない。
