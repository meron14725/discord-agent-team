# Issue #5 実装計画 v1

## 1. 実装境界と基本方針

対象は既存の `meron14725/discord-agent-team` であり、新規Discordアプリは作らない。初期対象は `coordinator`、`cto`、`backend_integrator`、`security_sre` の4役だけとする。既存の `CoordinationDecision` / `SpecialistDecision`、承認ゲート、委任・継続制御、SRE変更提案、Discord配信の重複抑止を変更せず、その周囲に次の二つを追加する。

1. 判断時プロンプトに、会社規則、役割規則に続く最低優先順位のPERSONAを役割IDで供給する。
2. 構造化判断の検証完了後、Discord配信前に限り、固定事実を変更できない `PersonaFormatter` を呼び出す。

優先順位は `会社規則・承認/標限/安全条件 > 役割規則 > 構造化出力契約 > PERSONA` とする。PERSONAは権限、action、ツール実行、承認、委任先、継続回数を決定しない。整形失敗時は判断を再実行せず、既存の決定的な安全返信を送る。

## 2. PERSONA定義と40会話例

版管理単位として次を新設する。

- `prompts/personas/coordinator/v1/PERSONA.md`
- `prompts/personas/cto/v1/PERSONA.md`
- `prompts/personas/backend_integrator/v1/PERSONA.md`
- `prompts/personas/security_sre/v1/PERSONA.md`

各ファイルの先頭に機械可読なメタデータ `role_id` と `version` を置き、本文には見出し `Identity`、`Character`、`Conversation`、`Voice`、`Examples` を各1回含める。Examplesは `Good-1`〜`Good-5` と `Bad-1`〜`Bad-5` のちょうど10件とし、各例へ `role_id`、`scenario`、`input`、`expected_decision`、悪い例では `violation_rule` を記載する。

役割差は語尾に依存させず、同一シナリオに対して次の判断基準を明示する。

- coordinator: 相談と正式案件を区別し、必要担当だけを選び、重複委任を避ける。
- cto: 要件・根拠・受入条件を先に固定し、不明点が実装結果を変える場合に停止する。
- backend_integrator: 承認済みACと変更・テスト証跡を対応させ、実装可能性と統合リスクを優先する。
- security_sre: 最小権限、秘密保護、影響・検証・復旧可能性を優先し、承認前の特権操作で停止する。

4役共通の比較シナリオを少なくとも「曖昧な相談」「実装依頼」「失敗報告」「秘密を含む依頼」「承認が必要な変更」にそろえ、優先順位、判断、質問、停止条件のいずれかが役割固有であることをレビュー表で確認する。

## 3. 読込、対応検証、プロンプト優先順位

`src/agent_team/prompt_context.py` の `AgentPromptContext` に `personas` と `persona_versions` を追加する。`read_required_prompt` と同等の欠落・空・文字数上限検査に加え、PERSONA専用ローダーで必須節、例数、メタデータ、ディレクトリの役割ID・版との一致を検証する。

`src/agent_team/config.py` に `PersonaSettings` を追加する。設定項目は `enabled`、`root`、`active_versions`、`max_characters`、`format_timeout_seconds`、`max_output_characters` とする。`active_versions` は初期4役を明示的に列挙し、未登録役、欠落版、重複版、別役メタデータを拒否する。aliasはRoleRegistryでcanonical roleへ解決してから同じPERSONAを参照するが、未知役や対象外役から別役PERSONAへフォールバックしない。

`src/agent_team/api.py` と `src/agent_team/engine.py` が構築するRunRequestへ、対象役に限り `trusted_persona` と `trusted_persona_version` を追加する。`src/agent_team/adapters/codex.py` の固定指示には、PERSONAが上位規則と構造化契約を上書きできないこと、競合時はPERSONAを無視することを明記する。会社規則、役割規則、PERSONAは別フィールドのまま渡し、文字列連結順だけに安全性を依存させない。

## 4. 固定事実モデルと整形境界

`src/agent_team/persona.py` を新設し、以下を実装する。

- `FixedFactEnvelope`: role_id、decision type、action、元reply、実行成否・未実行、承認状態・理由、handoff先、SRE変更計画、識別子、数量、決定的な次工程、メンション対象を保持する凍結モデル。
- `PersonaFormatRequest`: 固定事実、PERSONA版、表現対象の非制御テキストだけを格納する。
- `PersonaFormatResult`: 整形本文、参照したfact ID、質問数、例外的文数超過の理由コードを格納する厳格モデル。
- `PersonaFormatter` protocolと実運用アダプタ、テスト用fake。
- `format_or_fallback`: タイムアウト、例外、形式・不変条件検査、固定返信生成、監査メタデータ生成を一箇所に集約する。

固定事実はPydantic検証済みdecisionと、`specialist_next_step` / `task_next_step` など既存の決定的計算から制御層が生成する。整形器には秘密を除去した最小入力だけを渡す。action等を出力から逆算せず、整形後も元decisionを正本として保持する。事実を表す必須ブロックはfact IDと値を構造化出力で照合し、最終表示時に制御層が確定値から組み立てる。これにより人格処理が事実値を書き換えられない構造にする。

`src/agent_team/adapters/discord.py` の統括通常返信と専門役返信の共通送信直前に境界を置く。呼出順は `モデル判断 → CoordinationDecision/SpecialistDecision.model_validate → FixedFactEnvelope生成 → PersonaFormatter → 不変条件検証/フォールバック → 決定的な次工程・メンション付加 → discord_parts/send_chunked` とする。SRE plan提案やcontinue/handoffの制御分岐は元decisionだけを参照し、整形結果を制御入力にしない。

既存の `discord_delivery.py` の1800文字分割、イベントpart marker、履歴からの欠落partだけの再送、`AllowedMentions` は後段にそのまま残す。

## 5. 検証、フォールバック、冪等性

整形出力へ次の決定的検査を行う。

- 必須fact IDの欠落、重複、未知fact、値不一致を拒否する。
- 未実行時は実行済み・完了済みを表す禁止語と状態矛盾を拒否する。
- 疑問文は「？」等の表記と構造化question countの双方で最大1件にする。
- 通常返信は1〜4文。超過を許すのは、安全情報または検証情報の保持を示す定義済み理由コードがあり、必須factを削れない場合だけとする。
- 空、型不正、最大文字数超過、タイムアウト、内部例外を同じfail-closed経路へ送る。

フォールバックは元decision.replyと決定的な次工程から作る固定返信であり、モデルやエージェントを再呼出ししない。action、承認、実行、handoff、continuation、SRE planを更新せず、追加ツール・外部操作も行わない。

Discord送信の冪等キーは既存event_idを維持し、人格版や整形結果をキーに含めない。同じイベントの再試行で人格版が切り替わっても、既送partを別内容で上書きせず、既存マーカーにより欠落partだけを処理する。テストでは整形器が複数回呼ばれても元decision・外部操作数が増えないことを確認する。

## 6. セキュリティ、権限、監査、競合分析

秘密:

- token、認証header、raw tool payload、秘密検知対象文字列をPersonaFormatRequestへ渡さない。
- 既存 `SecretScanner` / redaction境界を整形入力前と出力後にも適用する。
- 監査ログには本文、秘密、承認tokenを含めず、role_id、persona_version、fallback boolean、fallback reason、fact ID一覧のdigest、検査結果、event_idだけを記録する。

認可:

- PERSONA設定はRoleRegistryの権限・capability・fallback roleを変更しない。
- PersonaFormatterはツール、DB更新、GitHub、Discord管理APIへアクセスしない。
- approval reasonと状態はFixedFactEnvelopeの読み取り専用値とし、整形成功を承認として扱わない。
- SRE変更は従来どおり元 `SpecialistDecision.sre_plan` と既存承認ゲートだけで処理する。

競合・race:

- 起動時または明示的再読込時に全4役のスナップショットを一括検証し、成功後にimmutable registryを原子的に差し替える。検証途中の版をリクエストへ露出しない。
- 1返信では選択済みのrole_id/versionスナップショットを最後まで固定し、再読込との混在を防ぐ。
- 同一イベントの同時送信は既存マーカー検査を維持する。必要なら既存outbox/eventの単一処理境界内で整形し、新しい独立した外部操作を作らない。
- タイムアウト後に遅れて完了した整形結果は破棄し、フォールバック送信後の二重送信を許さない。

## 9. マイグレーション、ロールアウト、ロールバック

DBスキーマ移行は行わない。人格版選択は設定と版付きファイル、監査は既存構造化ログを利用するため、`migrations/` の追加は不要である。実装時に永続的な版履歴が必要と判明した場合は要件外のDB変更を推測せず、別承認事項として停止する。

展開順:

1. 4役のv1、ローダー、整形器、テスト、運用手順を配置するが、初期設定は `enabled: false` とする。
2. 無効状態で既存の通常返信、委任、質問、承認待ち、継続、SRE変更提案、Discord配信回帰を実行する。
3. 非本番環境で1役ずつactive_versionsをv1へ設定し、起動時検証、固定事実監査、フォールバック注入試験を行う。
4. 4役有効時の全テストと40例レビューを完了し、別途必要な計画・実装・展開承認を得る。承認なしに本番適用しない。
5. 適用後はfallback率、timeout、不変条件拒否、role/version不整合を監視する。本文や秘密は監視へ出さない。

ロールバックは役割単位で `active_versions[role_id]` を直前の正常版へ戻し、定義済み再読込またはプロセス再起動後、監査ログのrole/versionとテスト返信で旧版適用を確認する。正常な旧版がない初回導入では `enabled: false` に戻し、既存固定返信経路を継続する。コードを緊急編集せずに対象版を設定から特定できる。既送Discordメッセージは編集・削除しない。
