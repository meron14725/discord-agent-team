# Company memory

## Thesis

Discordを唯一の日常インターフェースとして、1人のオーナーが複数の専門AIエージェントを安全に運営できる会社基盤を作る。

## Current wedge

自然なDiscord会話から、相談は相談として扱い、必要な専門家だけが応答する。具体的な開発依頼だけを、要件整理・承認・実装・独立レビュー・CI確認へ進める。

## Current stage

単一Discordサーバーと単一GitHub所有者で検証中の非公開プロトタイプ。現在の常設役は統括、上流、下流、情シス・SRE。将来は約10役まで増やす。

## Role registry and handoffs

- 統括: オーナーの窓口、担当選択、重複排除、優先順位、進行管理。
- 上流: 要件整理、設計、計画、リスク分析、独立レビュー。
- 下流: 実装、デバッグ、テスト、具体的なコード変更。
- 情シス・SRE: Discord管理、実行基盤、監視、障害対応、安全な運用。
- 各専門家は全役割を把握し、別担当の知見が必要なら統括の制御層へ型付き引き継ぎを提案する。
- 新規割当、再割当、特権操作は統括の制御層が検査する。通常の調査結果や助言は担当間で共有できる。
- 引き継ぎの回数、重複、承認、権限に関する拘束規則は `company-policy.md` を正本とする。

## Must build now

- 会話と案件の区別をモデルが文脈から判断する。
- 統括が適切な専門家を選び、専門家自身が独立して回答や確認を行う。
- 専門家が別担当を必要とした場合、安全な統括経由の引き継ぎを行う。
- コード変更は必ず仕様承認、隔離実行、独立レビュー、CIを通す。
- Discordや基盤の特権操作は、読み取り調査、型付き計画、安全検査、人間承認、監査の順に行う。

## Must not build yet

- 1つのエージェントに要件定義、実装、承認を兼任させない。
- 会話や曖昧な相談から自動でリポジトリを作らない。
- モデルへBot、GitHub、DB、Docker、OpenAIの秘密情報や直接操作権限を渡さない。
- 顧客、用途、検証目的が不明なまま大きな製品を一括実装しない。

## Evidence goal

オーナーがスラッシュコマンドを覚えずに会話でき、意図したときだけ案件が作られ、担当分離と安全確認を保ったまま成果物まで到達できることを実地で確認する。

## Decision rights

日常の会話、読み取り調査、助言、低リスクな整理は各エージェントが自律判断する。仕様確定、マージ、権限変更、削除、公開、課金を伴う操作はオーナーの明示承認を必要とする。
