# Discordからの承認付きDocker反映

## 利用の流れ

1. Discordで既存の `discord-agent-team` の改善を依頼する。
2. 要件・計画の承認、実装、CI、独立レビューを既存フローで行う。
3. オーナーがPRのマージを承認する。
4. マージが確定すると、統括が対象コミットSHAと影響を記載した反映案を出す。
5. オーナーが「このSHAをDockerへ反映」を押す。マージ承認とは別の承認。
6. ホストの独立した更新担当が事前検証・DBバックアップ・更新・稼働検証を行う。
7. 統括が結果をオーナーメンション付きで通知する。起動検証に失敗した場合は旧イメージへ戻す。

承認はデフォルト15分で失効する。期限切れや事前検証失敗の場合は、同じ案件の `/retry` で新しい承認案を出せる。使用済みボタンで再実行できない。ホストが停止している間も承認期限は延長されない。

## 自動反映の範囲

- 対象リポジトリは設定で指定した1件。対象SHAはそのリポジトリの現在の基準ブランチHEADであることをホストがGitで確認する。
- 対象SHAの必須CIを名前と発行GitHub App IDで再確認する。CI未完了・失敗は反映しない。
- Dockerの `orchestrator`、`discord-gateway`、`renderer` だけを更新する。
- 許可範囲は通常のsrc、tests、docs、ペルソナ。DB・設定モデル・Sandbox・Codex起動処理・権限規則・更新制御コード、Dockerfile、Compose、依存パッケージ、秘密情報、会社規則、ホストスクリプトは初期版の自動反映対象外。
- ホストで動くCodexワーカーや更新担当自身の更新は別途、人間による保守作業が必要。
- 新しいコードによる一般のデータ書き換えまで、イメージ切り戻しで取り消せるわけではない。データ変換を含む改善はこの経路に載せない。

## 権限の境界

`scripts/deploy_supervisor.py` はPython標準ライブラリだけで動く。レビュー済みのコピーを、Botにマウントしないホスト専用ディレクトリへ設置する。BotはDockerソケット、ホストのシェル、SSHの権限を持たない。更新担当は外部から接続するAPIサーバーを持たず、固定されたローカルDocker Composeコマンドだけを使う。

更新担当はホストユーザーのDocker権限を持つ信頼済みのプログラムである。OS上でDocker権限そのものがサービス3件だけに限定されるわけではない。このプログラムと設定をLLMの編集・実行領域から隔離することが必須。GitHubの読み取りにはホストのGit/gh認証を利用するが、トークンをBotへ渡さない。

承認待ち・実行結果は既存のOperation、Approval、Event、Outboxへ保存する。更新担当へのブリッジはローカルの `docker exec ... python -m agent_team.deployments` のみで、HTTPには公開しない。

## 起動と初回設定

初回のみ人間の監督下で、コントローラ・Gateway・rendererを本機能を含むイメージへ更新する。これが切り戻し可能な基準イメージになる。DBマイグレーションは追加していない。

ホスト専用設定には以下を指定する（認証情報は書かない）。

```json
{
  "project_root": "/absolute/path/to/discord-agent-team",
  "state_dir": "/private/host-only/deployment-state",
  "project_name": "discord-agent-team",
  "repository": "meron14725/discord-agent-team",
  "branch": "main",
  "baseline_sha": "初回稼働版の40桁のコミットSHA",
  "owner_ids": ["オーナーのDiscord ID"],
  "required_checks": [{"name": "tests", "app_id": 15368}]
}
```

macOSでは `scripts/install_deploy_supervisor.py --config <上記の設定JSON> --install-dir <ホスト専用ディレクトリ> --python <信頼済みPythonの絶対パス>` が、更新担当のコピー・設定・launchd用plistを設置する。既存インストールの上書きやプロジェクト内部への設置は拒否し、このコマンドだけでは起動しない。

設置したplistを `launchctl bootstrap gui/<UID> <plistの絶対パス>` で起動する。複数起動はローカルファイルロックで拒否する。Python 3.12以上、Docker Compose、Git、認証済みghが必要。Linuxでは同じsupervisorをsystemd等で起動できるが、インストール自動化と実機検証の対象は今回macOSのみ。

`config.yaml` の `deployment.enabled: true` と `deployment.repository_alias: discord-agent-team` を設定し、コントローラを再起動する。設定が無効な間は更新担当が稼働していてもジョブを取得しない。通常の他リポジトリ案件にも反映案は出さない。

この初回設定は過去のマージ済み案件を一斉に反映しない。初回設定後にマージされた案件が対象になる。

## 復旧と監視

- 実行中は新しい案件ジョブの取得と会話用モデル呼び出しを止め、既存ワーカーの稼働が終わるのを待つ。
- 更新前の3サービスのイメージIDをディスクに同期保存する。DBバックアップはホスト専用ディレクトリに0600相当で保存する。
- HTTPヘルス、実イメージID、Gatewayの全BotのDiscord接続状態を確認する。モデルの全業務の正しさを保証する検査ではない。
- 更新途中で更新担当が停止した場合、再起動時は成功と推測せず旧イメージへの復旧を優先する。
- DBバックアップを自動復元しない。反映後に発生したユーザーデータを上書きしないため。
- 復旧にも失敗した場合は追加反映を停止する。`deployment.json` / `last-result.json` とホストログを確認し、人間が復旧する。Bot全体が停止している間のDiscord通知は保証できず、コントローラが戻ってから結果通知を再送する。
- 出力ログには例外の種類・工程・操作IDのみを出す。コマンドの出力、秘密、バックアップ本文は出さない。
- 手動でComposeを操作する際、更新担当が保存した `runtime.override.json` を最後の `-f` に含める。含めない場合はComposeの元のイメージ指定へ戻る可能性がある。
- バックアップとビルドイメージは自動削除しない。保持量とディスク空きをSREが監視し、削除は別の保守作業として扱う。

## 検証

`tests/test_deployments.py` は実際の承認ボタンAPIからDB操作を通し、オーナー照合、SHA不一致、期限切れ、二重クリック、実行中ジョブ、事前検証拒否、起動失敗時の切り戻し、更新担当の再起動、通知再送を確認する。Docker操作は通常の単体テストでは代替実装を使い、本番サービスを更新しない。

運用開始前に、別Composeプロジェクト・本番認証情報なしで、正常起動と意図的な起動失敗からの復旧も確認する。

2026-09-15に独立した `discord-release-poc` プロジェクトで実施済み。正常な3コンテナを起動後、起動直後に終了するイメージへ更新し、稼働検証失敗を検出。保存した3件の元イメージIDへ戻り、HTTPとGateway接続状態の検査が成功することを確認した。検証用コンテナは削除済み。本番での承認から反映までの初回確認は、有効化後の最初の案件で行う。
