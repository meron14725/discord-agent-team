# Issue #5 実装計画 v3

## 実装方針

既存基盤へ、初期4役 `coordinator`、`cto`、`backend_integrator`、`security_sre` の版付きPERSONA定義と、構造化判断確定後に返信表現だけを整えるペルソナUI層を追加する。新規Discordアプリ、長期記憶、会話からの自己更新、自動学習は追加しない。

優先順位は、会社規則・権限・安全条件・人間承認、役割規則、構造化出力契約、PERSONAの順とする。PERSONAはaction、承認状態、実行状態、委任先、継続回数、SRE変更計画を決定せず、上位規則と競合する指示を適用しない。

処理順は以下とする。

1. モデルが `CoordinationDecision` または `SpecialistDecision` を生成する。
2. 既存契約で構造化判断を検証する。
3. 権威ある構造化値から `FixedFactEnvelope` を決定的に生成する。
4. 選択済みrole/versionのPERSONAで本文を整形する。
5. 制御層が原文保持ブロック、承認・実行状態、次工程などの決定的ブロックを合成する。
6. 合成後の最終返信全体に、固定事実、未実行矛盾、質問数、文数例外理由、文字数、秘密、メンション制御の検査を適用する。
7. 合格時だけ `discord_parts` / `send_chunked` へ渡す。不合格時は自由文を破棄し、検証済みEnvelopeから決定的fallbackを生成して同じ最終検査へ通す。
8. 後続制御は常に元decisionを参照し、整形本文を制御入力にしない。

`FixedFactEnvelope` は自由文から推測せず、decision型、action、role_id、task/event ID、workflow/tool status、operation ID、対象、数量、error code、approval state/reason、委任・handoff、continuation instruction、task summary、next-step、検証済み `DiscordSREPlan` から決定的に構築する。承認token、認証情報、raw tool payloadは含めない。

fallbackは `decision.reply` を再利用せず、Envelopeの列挙値を固定テンプレートへ埋めて生成する。判断再実行、追加操作、権限拡張、承認変更は行わない。固定テンプレートも最終検査に失敗した場合は配信せず、本文を含まない内部安全エラーだけを記録する。

## セキュリティ

`PersonaFormatRequest` へtoken、認証header、raw tool payload、承認tokenを渡さない。入力前、整形後、原文保持ブロック、合成後最終返信に既存redactionを適用する。

監査には返信本文や秘密を含めず、event ID、role ID、persona version、fallback有無・理由、fact ID集合のdigest、最終検査結果だけを記録する。秘密を検出した候補は破棄し、秘密を含まないEnvelope由来テンプレートへfallbackする。PERSONAファイルにも秘密検査を適用する。

## 冪等

既存event IDとpart markerを維持し、persona versionや整形本文を送信冪等キーへ加えない。同一イベントの再試行では既送partを編集せず、欠落partだけを送る。

Formatter、合成、検査、fallbackを副作用のない処理とし、再実行しても元decision、workflow、承認、外部操作回数を変更しない。timeout後に完了した遅延結果は破棄し、fallbackとの二重送信を防ぐ。

## 競合

4役のPERSONAを一括検証してからimmutable registryを原子的に差し替える。失敗時は現行registryを維持し、別役へ暗黙切替しない。

各返信はrole/versionのスナップショットを完了まで固定し、再読込との版混在を防ぐ。同一eventの並行処理は既存outbox/marker境界で抑止し、整形成功とfallbackの競争による二重送信を禁止する。

## 権限

PERSONA設定はRoleRegistryのcapability、fallback role、委任先、承認ゲートを変更しない。Formatter、合成器、検査器はツール、DB更新、GitHub、Discord管理APIを呼べない純粋境界にする。

整形成功や自然言語上の同意を承認として扱わない。SRE変更は元decisionと既存承認ゲートだけで処理する。設定変更、再読込、本番有効化、GitHub公開・マージは別の人間承認対象であり、本計画では実施しない。

## ロールアウト

1. v1定義、ローダー、Formatter、最終検査、テスト、runbookを `enabled: false` で配置する。
2. 無効状態で通常返信、委任、質問、承認待ち、継続、SRE提案、Discord配信の回帰を完了する。
3. 非本番で1役ずつ有効化し、起動検証、不変条件監査、全fallback原因、原文保持ブロック由来の矛盾・複数質問・文数超過を注入試験する。
4. 4役、40例、AC-001〜AC-020の証跡を個別に確認し、計画・実装・展開の必要な承認を得る。承認なしに本番適用しない。
5. 適用後はfallback率、timeout、最終検査拒否、role/version不一致のみ監視し、本文や秘密を収集しない。

## マイグレーション

DBスキーマ移行は行わず、`migrations/` は変更しない。版選択は設定と版付きファイル、監査は既存構造化ログを利用する。

persona設定がなければ `enabled: false` と同等に扱う。未知役を別役へ対応させない。永続的な版履歴や新規DB列が必要と判明した場合は要件外変更として停止し、別途要件と承認を求める。

## ロールバック

役割単位で `active_versions[role_id]` を直前の正常版へ戻し、原子的再読込またはプロセス再起動後、テスト返信と監査のrole/version一致を確認する。統合テストでは正常なv1/v2 fixtureを使って二版間切戻しを検証する。

初回導入で直前正常版がなければ `enabled: false` に戻して既存返信を継続するが、これはAC-016の二版間切戻しテストの代替にはしない。既送Discordメッセージは編集・削除しない。

## 未確認事項

実装を妨げる要件上の未確認事項はない。初期対象4役とAC-001〜AC-020は承認済み要件の範囲で確定している。計画、実装、展開、公開、マージは未承認であり、本計画から承認を推定しない。

文字数上限、整形timeout、再読込方式の具体値は既存運用値を測定し、実装計画承認後に設定する。具体値にかかわらず、fail-closed、役割取り違え禁止、無効時の既存経路継続、合成後の最終不変条件検査は変更しない。
