# Issue #5 実装計画 v2

## 実装方針

既存基盤へ、初期4役 `coordinator`、`cto`、`backend_integrator`、`security_sre` の版付きPERSONA定義と、構造化判断検証後・Discord配信前だけで動くペルソナUI層を追加する。新規Discordアプリ、長期記憶、自己更新、自動学習は追加しない。

優先順位は、会社規則・権限・安全条件・人間承認、役割規則、構造化出力契約、PERSONAの順とする。PERSONAはaction、承認、実行状態、委任先、継続回数、SRE計画を決定せず、競合時は適用しない。

呼出順は `モデル判断 → CoordinationDecision/SpecialistDecision検証 → 固定事実生成 → PERSONA整形 → 不変条件検査または決定的フォールバック → 制御層ブロック付加 → discord_parts/send_chunked` とする。後続の制御分岐は常に元decisionを参照し、整形本文を制御入力にしない。

## PERSONA定義

4役それぞれに版付き `PERSONA.md` を置く。メタデータとして `role_id` と `version`、本文に `Identity`、`Character`、`Conversation`、`Voice`、`Examples` を含める。各役のExamplesは `Good-1`〜`Good-5`、`Bad-1`〜`Bad-5` のちょうど10件とし、全例に `example_id`、`role_id`、`scenario`、`input`、`expected_decision`、悪い例には `violation_rule` を持たせる。

共通シナリオを使い、役割差を語尾ではなく判断基準で示す。coordinatorは相談と案件の区別・必要担当だけの選択、ctoは要件・根拠・ACの固定、backend_integratorはACと変更・テスト証跡の対応、security_sreは最小権限・秘密保護・承認前停止を優先する。

## 固定事実とフォールバック

`FixedFactEnvelope` は自由文から事実を抽出して作らない。各返信経路について、次の権威ある構造化入力からfact IDへ決定的に写像する。

- 共通: decision型、action、role_id、task/event識別子。
- 成功・失敗・未実行: workflow/tool resultの構造化status、operation ID、対象、数量、error code。
- 承認待ち: approval state、approval reason、対象操作。承認token自体は渡さない。
- 委任: `CoordinationDecision.delegations` または `SpecialistDecision.handoffs` のroleとinstruction識別子。
- 継続・質問・案件提案: action、continuation instruction、task summary、決定的next-step。
- SRE変更提案: 検証済み `DiscordSREPlan` のoperation、guild/target/parent ID、name/topic、archive、reason、impact、verification、rollback。

元replyにしか存在しない構造化されていない内容は人格整形へ渡さず、秘匿化・長さ検査済みの「原文保持ブロック」として制御層がそのまま付加する。安全上重要な識別子、対象、数量がreplyにしか存在する設計箇所が見つかった場合は、推測抽出せず対応する構造化モデルを追加してから整形対象にする。

フォールバック本文は自由文の `decision.reply` を再利用しない。検証済みEnvelopeの列挙値を、action/state別の固定テンプレートへ埋めて制御層が決定的に生成する。テンプレートは未実行を完了と表現せず、原則質問を生成せず、必要な確認がある場合も1件だけとする。通常1〜4文とし、安全情報または検証情報が不可欠な場合だけ理由コード付きで超過を許す。

整形出力とフォールバック最終出力の双方へ、必須factの欠落・重複・未知fact・値不一致、識別子・対象・数量の改変、未実行との矛盾、質問数、文数、文字数上限、秘密検査を適用する。固定テンプレート自体が検査に失敗した場合は送信せず内部安全エラーとして記録するが、テンプレートを網羅テストして通常到達不能にする。フォールバックでは判断再実行、追加操作、権限拡張、承認変更を行わない。

安全不変条件と人格品質は別テスト群にし、不変条件違反は人格評価にかかわらず不合格とする。外部Discord、本番、特権操作は使用せずfake formatter/channelと既存mockで完結させる。

## セキュリティ

PersonaFormatRequestへtoken、認証header、raw tool payload、承認tokenを渡さない。既存redactionを入力前と出力後に適用し、原文保持ブロックにも同じ検査を行う。監査には本文を含めず、event ID、role ID、persona version、fallback有無・理由、fact ID集合のdigest、検査結果だけを残す。

秘密が検出された整形出力は破棄し、秘密を含まない決定的テンプレートへフォールバックする。PERSONAファイル自体にも秘密検査を適用する。

## 権限

PERSONA設定はRoleRegistryのcapability、fallback role、委任先、承認ゲートを変更しない。Formatterはツール、DB更新、GitHub、Discord管理APIを呼び出せない純粋境界にする。整形成功を承認として扱わず、SRE変更は元decisionと既存承認ゲートだけで処理する。

## 冪等

既存event IDとpart markerを維持し、人格版や整形本文を送信冪等キーへ加えない。同一イベントの再試行では既送partを編集せず、欠落partだけを送る。Formatterが複数回呼ばれても元decision、workflow状態、外部操作回数が増えないことを検査する。

## 競合

4役分のPERSONAを一括検証後、immutable registryを原子的に差し替える。各返信は選択済みrole/versionスナップショットを処理終了まで固定し、再読込との版混在を防ぐ。timeout後に完了した結果は破棄し、フォールバック後の二重送信を禁止する。同一eventの競合は既存outbox/marker境界内で処理する。

## ロールアウト

1. v1定義、ローダー、Formatter、テスト、runbookを `enabled: false` で配置する。
2. 無効状態で通常返信、委任、質問、承認待ち、継続、SRE提案、Discord配信の回帰を完了する。
3. 非本番で1役ずつv1を有効化し、起動検証、不変条件監査、全fallback原因を注入試験する。
4. 4役・40例・全ACの証跡を確認し、別途必要な計画・実装・展開承認を得る。承認なしに本番適用しない。
5. 適用後はfallback率、timeout、不変条件拒否、role/version不一致だけを監視し、本文や秘密を収集しない。

## マイグレーション

DBスキーマ移行は行わない。版は設定と版付きファイル、監査は既存構造化ログを利用するため `migrations/` は変更しない。永続的な版履歴や新規DB列が必要と判明した場合は要件外変更として停止し、別承認を求める。

設定移行は後方互換とし、persona設定が存在しない場合は `enabled: false` と同等に扱う。未知役を別役へ暗黙対応させない。

## ロールバック

役割単位で `active_versions[role_id]` を直前の正常版へ戻し、原子的再読込またはプロセス再起動後、テスト返信と監査のrole/version一致を確認する。統合テストでは同一役の正常なv1/v2 fixtureを用い、v2選択後にv1へ戻して、返信へv1が適用されるところまで検証する。

初回導入で実運用上の旧版がない場合は `enabled: false` に戻して既存返信を継続する。これは安全停止手段であり、AC-016の二版間切戻しテストの代替にはしない。既送Discordメッセージは編集・削除しない。

## 未確認事項

実装を妨げる要件上の未確認事項はない。初期4役とAC-001〜AC-020は承認済みである。

文字数上限、整形timeout、再読込方式の具体値は既存運用値の測定後に設定する。選択にかかわらず、fail-closed、役割取り違え禁止、無効時の既存経路継続、不変条件維持は変更しない。
