# AI10役への拡張

結論: **Discordを窓口、DBを状態の正本、ジョブを仕事の単位にする構成はAI10役へ拡張可能です。**
ただし現在のコードが設定変更だけで10役になるわけではありません。現在の契約・ワーカー・役割の分岐は開発2役専用です。
10役の同時稼働性能や、このサブスク契約で処理できる案件数は未測定です。

## 増やし方

「役割数」と「同時にモデルを呼ぶ数」は別々にします。役割は指示・成果物・権限の組であり、待機中はモデルを動かしません。
同じサブスクを使う初期段階は、10役から届く仕事を1実行枠で順番に処理できます。
この実装もchatgpt認証では全役を通じ1件に制限し、認証更新の競合と利用枠への急な負荷を抑えています。

| 段階 | 役割の例 | 必要な変更 |
|---|---|---|
| 現在 | 要件・レビュー、実装・修正 | 2役の動作確認と運用 |
| 4役 | 統括・PM、設計・レビュー、実装、情シス・SRE | role registry、役別schema・プロンプト、統括からの明示的ジョブ生成 |
| 6〜10役 | 調査、デザイン、コンテンツ、営業支援、経理補助、運用分析など | 業務別ワークフロー・成果物・ツール許可・承認ゲート |

営業AIによる外部送信や経理AIによる支払いは、開発PRの承認と同じ扱いにはできません。
最初は調査レポート・メール草案・仕訳案までを成果物にし、人間が承認してから外部操作する契約を追加します。
AIが自分でAIを無制限に増やしたり、役割設定を変更したりする方式にはしません。

## 統括・PMエージェント

ユーザーは最初に目的を伝え、仕様・支出・公開・マージなど重要な判断だけ承認する。
統括は依頼を子タスクへ分け、適切な役へ割り当て、進捗と失敗を監視し、許可済みの安全な再試行を行う。
情シス・SREの診断で復旧条件を満たした場合も、統括が元の担当へ自動で戻す。

統括は資格情報を持つ自由実行エージェントにはしない。DBへ直接任意の状態を書かず、
制御プログラムが許可した状態遷移・ジョブ種別だけを提案できる。
要件変更、外部送信、課金、権限変更、公開、マージは業務ごとの承認ゲートを維持する。
Discordでは通常の`/retry`や担当指定をユーザーへ要求せず、判断が必要な時だけ選択肢と根拠を通知する。
入口はgeneralの通常メッセージとし、初期構成では既定の`project`へ割り当てる。
有効化後の新規投稿だけを受け付け、過去ログを新規案件として再処理しない。
Discord上は統括、上流、下流、情シス・SREの4 Botを使用する。統括だけがgeneralの本文を読み、
専門Botは担当スレッドへ質問・作業結果・障害報告を表示する。内部の制御プログラムは全Botの
認証・状態遷移・ジョブ投入を検査し、Bot同士の発言を新しい依頼として読み戻さない。

第一段階として、以前の失敗が実行ファイル未検出（終了コード126/127）で、信頼済み設定の
テストコマンドがその後変更された場合に限り、統括ロジックが新しい実装ジョブを自動登録する。
保存済みの失敗結果は再利用しない。仕様hashが変わった場合や認証・権限エラーは自動再開しない。

## 10役化する実装順序

1. 統括・PMと情シス・SREを追加し、安全な自動割当・復旧と人間への判断依頼を分離。
2. `RunRequest.role`と`Result`を、固定2役からホスト管理のrole registryと業務別schemaへ移行。
3. `jobs`に依存ジョブID・優先度・roleごとの実行枠を追加。`tasks`は会社横断案件、業務別子タスクを持つ。
4. 開発案件ごとに異なるrepoを使う現在の割当を維持し、repo単位の実装ロックを導入。開発以外の仕事はrepoを必須にしない。
5. `claim`の予算集計をDB集計・予算予約台帳へ移し、モデル実行数・待ち時間・成功率・修正回数を役別に計測。
6. Discordはgeneralを受付、リポジトリごとに専用チャンネル、案件・話題ごとにスレッドを作る。対応は名前でなくDBのrepository IDとchannel IDで管理する。
7. 常時稼働サーバへ移行し、監視・バックアップ・秘密更新・再認証の担当手順を固める。

当面、PostgreSQLのキューとComposeを使い続ける設計でよく、役割数だけを理由にRedisやKubernetesを追加する必要はありません。
これは本システムの設計判断です。単一制御プロセスにはリーダーロックがあるため、制御サービスの水平増設には別の設計が必要です。

## 次に追加する役: 情シス／SRE

開発2役の実動確認後、3役目として情シス／SREエージェントを追加する。
今回発生したGitHubの反映待ち、`python` / `python3`の実行環境差、Docker Sandbox、
Discord Bot、GitHub App、CI、常駐サービスの障害を分類・診断する。

- 明確な一時障害や既知の安全な復旧は、制御層のルールに従って再試行する。
- 設定・コード修正は管理用リポジトリへPRとして提案し、テスト結果とロールバック手順を付ける。
- Bot/GitHub/OpenAIの秘密値はモデルへ渡さず、資格情報の中身もログへ出さない。
- 認証・権限、Sandbox境界、承認ルール、データ削除、デプロイは人間承認後に実行する。
- 案件担当の下流エージェントには基盤を直接変更させない。案件コードと運用基盤のレビュー主体を分離する。
- 起動前のtoolchain検査で、設定したテストコマンドや必要なCLIがSandbox内に存在するか確認する。

実装には、role registry、`platform_diagnose` / `platform_repair`ジョブ、障害分類schema、
管理リポジトリ、修正PRの承認・適用・ロールバック状態を追加する。

## 制約になりやすいもの

- **サブスクの利用枠**: 役を増やしても契約上の枠は増えません。現在のCodexアプリでの作業とも利用枠を共有します。利用上限・ログイン失効はBlockedへ戻し、API課金へ自動で切り替えません。
- **待ち時間**: 1件ずつ20分使う仕事が10個あれば、最後の仕事の開始まで最大約180分待ち得ます。仕事を短く区切り、不要なAI間会話を減らす方が先です。
- **PC稼働時間**: PC停止中は会社基盤も停止します。無人継続運転には常時稼働ホストが必要です。
- **ビルド資源**: モデル推論は外部ですが、テスト・ブラウザ・ビルドはホスト資源を使います。4 vCPU・8 GiBの仮置きから実測し、必要なら16 GiB以上へ増強を検討します。性能保証ではありません。
- **人間の承認待ち**: 10役を増やすだけでは解消しません。低リスク操作の条件を業務ごとに固めてから自動化します。

ChatGPTログインはサブスク利用、APIキーは従量課金という別の認証経路です。無人環境の認証保存と更新は公式の方法に従います。
[OpenAI: Authentication](https://learn.chatgpt.com/docs/auth)、[CI/CDでの認証維持](https://learn.chatgpt.com/docs/auth/ci-cd-auth)。
