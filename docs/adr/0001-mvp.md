# ADR 0001: 信頼境界と段階的実接続

日付: 2026-09-12

元仕様の2開発役を実装。追加要望により、固定repoだけでなく `meron14725` 配下の案件別repo作成、ChatGPTサブスク認証を追加した。
元仕様は原文のまま保存する。

- 制御・GitHubアダプターは同じ信頼プロセスに統合。Discord Gateway、上流ワーカー、下流ワーカー、DBは別コンテナ。
- 上下流ワーカーはDBネットワーク・Bot/GitHubの秘密に接続させない。各ワーカーのネットワークを分け、制御APIはgateway用認証を必須にする。
- sourceはGitHub REST tree/blobから独立した一時ディレクトリに展開。Git認証をcloneに渡さず、成果物はJSONで回収。小規模UTF-8リポジトリのみ。
- publisherはGit object APIでfeature branchを更新。force pushやbaseへの直接pushの経路を持たない。
- 新repoは仕様承認後にownerのユーザートークンで作成。private固定を初期値とし、案件IDの名前とdescription markerで再送を照合する。任意のDiscord入力URLでrepo操作しない。
- 既存repoのbaseはmasterを初期値、新規repoの接続例はmain。実在するbranchが必要で、見つからなくても勝手に作らない。
- テンプレートrepoの指定を推奨。テンプレートなしの場合はREADME付き初期repoを作るが、CI・保護ルールは自動で準備しない。
- サブスクは専用named volumeのCodex authを維持。ホストHOME全体を渡さない。認証更新はCodexに任せ、独自のOAuthリフレッシュ処理は書かない。chatgptモードのモデル実行は全体1件。
- APIキー方式も選択可能だが明示設定が必要。サブスクからAPIキーへのfallbackは行わない。
- 承認hash・SHA・CI発行Appを機械的に検査。APIの期待head SHA指定と厳格なbase追従保護を併用する。
- base更新や分類できないCI失敗はBlocked。初期版では自動rebaseや推測に基づくコード修正を行わない。
- DBリーダーロックは同じDBを使う重複制御プロセスを防ぐ。別々に復元したDB間の二重稼働は防げないため、移行元停止を運用要件とする。

Dockerの外向き通信はまだドメイン許可リストで強制していない。実行対象は自分が信頼するrepoのみ。
モデル認証はワーカーから使える。悪意あるコードに対する完全な秘密隔離は未達で、認証プロキシ等は次段階の課題。
