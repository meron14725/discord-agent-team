# ADR 0006: 実装計画を版付きの独立ゲートにする

## Status

Accepted.

## Decision

実装計画の作成とコード変更を別の実行に分ける。下流は案件ブランチの `docs/work-items/issue-<番号>/plans/v<版>.md` に計画を保存し、要件Issueから参照できるようにする。制御層は計画の版とハッシュを記録し、別セッションの上流によるレビューとオーナーによる計画版の承認がそろうまでコード実装を開始しない。

上流から下流への実装引き継ぎには、Issue番号とURL、承認済み要件の版とハッシュ、対象リポジトリ、基準コミット、対象範囲、受入条件ID、制約、相談記録を含める。制御層は引き継ぎ時のIssue本文が承認版と一致することを検査し、不一致なら要件定義へ差し戻す。

実装計画には、変更予定ファイル、設計とデータフロー、受入条件とテストの対応表、テストコマンド、手動確認、セキュリティ、展開とロールバック方法を記載する。上流は全受入条件の網羅と重要指摘の解消を確認する。レビュー済み計画の説明成果物を生成し、オーナーが理解して承認した計画版だけを実装に渡す。

上流のレビュー指摘と下流の計画修正は最大3回とする。解決しない場合は争点と推奨判断をオーナーへ戻す。承認後の実装は新しい下流セッションで開始し、承認要件と承認済み計画版を入力にする。

各モデル呼び出しは一時セッションとして実行し、要件Issue、計画、相談記録、DBの識別情報から必要な状態を復元する。要件定義、計画作成、計画レビュー、実装、実装後レビューの間で暗黙の会話状態を共有しない。

実装後レビューは、実装した下流とは別セッションの上流が最低1名で担当する。案件のリスクに応じて専門役を最大4件まで並列に参加させ、要件、計画、セキュリティ、テストへの適合を確認する。レビューと下流の修正は最大3回とし、解決しない重大な指摘はオーナーへ戻す。

案件成果物は `docs/work-items/issue-<番号>/` にまとめる。直下の `README.md` は要件Issue、承認版、現在の計画版、説明成果物、相談記録への索引とし、要件本文は複製しない。実装計画は `plans/`、要件と計画の説明用HTML・PNGは `explanations/requirements/` と `explanations/plans/` に保存する。

## Consequences

モデル実行回数と着手までの時間は増えるが、コードが生成される前に設計上の誤りを修正できる。案件単位のディレクトリと索引が最終PRにも残り、コードに現れない判断理由を将来の担当が追跡できる。
