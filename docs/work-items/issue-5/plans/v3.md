# Issue #5 実装計画 v3

## 実装方針

既存基盤へ、初期4役 `coordinator`、`cto`、`backend_integrator`、`security_sre` の版付きPERSONA定義と、構造化判断の確定後に返信表現だけを整えるペルソナUI層を追加する。新規Discordアプリ、長期記憶、会話からの自己更新、自動学習は追加しない。

優先順位は、会社規則・権限・安全条件・人間承認、役割規則、構造化出力契約、PERSONAの順とする。PERSONAはaction、承認状態、実行状態、委任先、継続回数、SRE変更計画を決定せず、上位規則と競合する指示は適用しない。

処理順は次のとおりとする。

1. モデルが `CoordinationDecision` または `SpecialistDecision` を生成する。
2. 既存契約で構造化判断を検証する。
3. 権威ある構造化値から `FixedFactEnvelope` を決定的に生成する。
4. 選択済みrole/versionのPERSONAで本文を整形する。
5. 制御層が、必要な原文保持ブロック、承認・実行状態、次工程などの決定的ブロックを付加して最終返信候補を合成する。
6. 原文保持ブロックを含む最終返信候補全体に対し、固定事実、未実行矛盾、質問数、文数例外理由、文字数、秘密、メンション制御を検査する。
7. 検査合格時だけ `discord_parts` / `send_chunked` へ渡す。不合格時は矛盾する自由文を破棄し、検証済みEnvelopeから決定的フォールバックを生成して同じ最終検査を行う。
8. 後続の制御分岐は常に元decisionを参照し、整形本文や最終返信を制御入力にしない。

### PERSONA定義

4役それぞれに版付き `PERSONA.md` を置く。メタデータとして `role_id` と `version`、本文に `Identity`、`Character`、`Conversation`、`Voice`、`Examples` を含める。

各役のExamplesは `Good-1`〜`Good-5`、`Bad-1`〜`Bad-5` のちょうど10件とする。全例に `example_id`、`role_id`、`scenario`、`input`、`expected_decision` を持たせ、悪い例には評価可能な `violation_rule` を必須とする。

共通シナリオで役割差を比較し、語尾ではなく次の判断基準を表す。

- coordinator: 相談と案件の区別、必要な担当だけの選択、委任重複の回避。
- cto: 要件、根拠、受入条件の固定と曖昧時の停止。
- backend_integrator: AC、変更ファイル、テスト証跡の対応と未承認実装の停止。
- security_sre: 最小権限、秘密保護、影響確認、承認前停止。

### 固定事実と最終返信検査

`FixedFactEnvelope` は自由文から抽出しない。次の権威ある入力からfact IDへ決定的に写像する。

- 共通: decision型、action、role_id、task/event識別子。
- 成功・失敗・未実行: workflow/tool resultのstatus、operation ID、対象、数量、error code。
- 承認待ち: approval state、approval reason、対象操作。承認tokenは含めない。
- 委任: `CoordinationDecision.delegations` または `SpecialistDecision.handoffs` のroleとinstruction識別子。
- 継続・質問・案件提案: action、continuation instruction、task summary、決定的next-step。
- SRE変更提案: 検証済み `DiscordSREPlan` のoperation、対象ID、name/topic、archive、reason、impact、verification、rollback。

元replyにしか存在しない非構造化内容は人格整形の固定事実にしない。必要なら秘匿化・長さ検査済みの原文保持ブロックとして合成するが、合成後の最終返信全体を必ず再検査する。安全上重要な識別子、対象、数量がreplyにしか存在する箇所は推測抽出せず、対応する後方互換な構造化フィールドを追加してから整形対象にする。

最終返信検査では、必須factの欠落・重複・未知fact・値不一致、識別子・対象・数量の改変、未実行と完了表現の矛盾、質問数、文数と例外理由、Discord文字数、秘密、メンションを確認する。通常は1〜4文、質問は最大1件とし、文数超過は必要な安全情報または検証情報と機械判定可能な理由コードがある場合だけ認める。

### フォールバック

フォールバックは自由文の `decision.reply` を再利用せず、検証済みEnvelopeの列挙値をaction/state別の固定テンプレートへ埋めて決定的に生成する。判断再実行、追加操作、権限拡張、承認状態変更は行わない。

整形失敗、タイムアウト、不正・空・上限超過出力、内部例外、原文保持ブロックを含む最終合成検査不合格をフォールバック原因とする。フォールバック出力も配信前に同じ最終検査へ通す。固定テンプレートまで不合格の場合は配信せず、本文を含まない内部安全エラーを記録する。テンプレート全組合せを網羅テストし、この経路を通常到達不能にする。

## セキュリティ

`PersonaFormatRequest` へtoken、認証header、raw tool payload、承認tokenを渡さない。既存redactionを入力前、整形出力後、原文保持ブロック、全ブロック合成後の最終返信に適用する。

監査には返信本文や秘密を含めず、event ID、role ID、persona version、fallback有無・理由、fact ID集合のdigest、最終検査結果だけを記録する。秘密を検出した候補出力は破棄し、秘密を含まないEnvelope由来テンプレートへフォールバックする。PERSONAファイル自体にも秘密検査を適用する。

## 冪等

既存event IDとpart markerを維持し、persona versionや整形本文を送信冪等キーへ加えない。同一イベントの再試行では既送partを編集せず、欠落partだけを送る。

Formatter、最終返信合成、検査、フォールバックは副作用のない処理とし、複数回実行されても元decision、workflow状態、承認状態、外部操作回数を変更しないことを検査する。タイムアウト後に遅延完了した整形結果は破棄し、フォールバックとの二重送信を防ぐ。

## 競合

4役分のPERSONAを一括検証した後、immutable registryを原子的に差し替える。検証失敗時は現行registryを維持し、別役への暗黙切替を行わない。

各返信は選択済みrole/versionのスナップショットを処理終了まで固定し、再読込との版混在を防ぐ。同一eventの並行処理は既存outbox/marker境界で抑止し、最終検査合格結果とfallback結果の競争による二重送信を禁止する。

## 権限

PERSONA設定はRoleRegistryのcapability、fallback role、委任先、承認ゲートを変更しない。Formatter、合成器、検査器はツール、DB更新、GitHub、Discord管理APIを呼べない純粋境界にする。

整形成功や自然言語上の同意を承認として扱わない。SRE変更は元decisionと既存承認ゲートだけで処理する。設定変更、再読込、本番有効化、GitHub公開・マージは別途定義された人間承認の対象とし、本計画では実施しない。

## ロールアウト

1. v1定義、ローダー、Formatter、最終返信検査、テスト、runbookを `enabled: false` で配置する。
2. 無効状態で通常返信、委任、質問、承認待ち、継続、SRE提案、Discord配信の全回帰を完了する。
3. 非本番で1役ずつv1を有効化し、起動検証、不変条件監査、全fallback原因、原文保持ブロック由来の矛盾・複数質問・文数超過を注入試験する。
4. 4役、40例、AC-001〜AC-020の証跡を確認し、必要な計画・実装・展開承認を個別に得る。承認なしに本番適用しない。
5. 適用後はfallback率、timeout、最終検査拒否、role/version不一致だけを監視し、本文や秘密を収集しない。

## マイグレーション

DBスキーマ移行は行わない。版選択は設定と版付きファイル、監査は既存構造化ログを利用し、`migrations/` は変更しない。

persona設定が存在しない場合は `enabled: false` と同等に扱う。未知役を別役へ暗黙対応させない。永続的な版履歴や新規DB列が必要と判明した場合は要件外変更として停止し、別途要件・承認を求める。

## ロールバック

役割単位で `active_versions[role_id]` を直前の正常版へ戻し、原子的再読込またはプロセス再起動後、テスト返信と監査のrole/version一致を確認する。統合テストでは同一役の正常なv1/v2 fixtureを使い、v2選択後にv1へ戻して返信へv1が適用されるまでを検証する。

初回導入で直前正常版が存在しない場合は `enabled: false` に戻し、既存返信を継続する。これは運用上の安全停止手段であり、AC-016の二版間切戻しテストの代替にはしない。既送Discordメッセージは編集・削除しない。

## 未確認事項

実装を妨げる要件上の未確認事項はない。初期対象4役およびAC-001〜AC-020は、提示された要件承認記録の範囲で実装計画の対象として確定している。計画、実装、展開、マージは未承認であり、本計画から承認を推定しない。

文字数上限、整形timeout、再読込方式の具体値は既存運用値を測定して実装計画承認後に設定する。値の選択にかかわらず、fail-closed、役割取り違え禁止、無効時の既存経路継続、最終合成後の不変条件検査は変更しない。
